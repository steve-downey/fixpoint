# Deviations from docs/freer-signature-functor-design.org

Reality wins; the design doc catches up. One row per contradiction
between what a step had to do and what the FD-series says. The
orchestrator reviews each row and folds accepted deviations back into
the design doc (updating the affected FD's status/rationale).

| ID | Step | FD affected | What the design said | What reality required | Handoff |
|----|------|-------------|----------------------|-----------------------|---------|
| DEV-S00-1 | S00 | FD9, FD12 | "libc++ shipped `std::move_only_function` only in LLVM 20" (FD9 toolchain-floor paragraph); FD12 frames libc++ availability as a version-gate problem. | Under the locally installed libc++-23-dev (LLVM 23 packaged build) `std::move_only_function` is not merely untagged by the feature macro — `clang++-23 -stdlib=libc++` rejects `std::move_only_function<int(int)&&>` outright ("no template named 'move_only_function' in namespace 'std'"); `<version>`'s `# define __cpp_lib_move_only_function` line is present but commented out. So at least as of this LLVM 23 snapshot, libc++'s gap is non-implementation, not just a missing feature-test macro. | `ops/freer/handoffs/00-ground.handoff.md` |
| DEV-S01-1 | S01 | FD3, FD5, FD9 | FD3's "Consequence worth recording" paragraph frames the hand-written non-defaulted `operator==` on `Free` as what keeps `impure_node`'s non-comparability from ever surfacing as an eager error, implying `std::equality_comparable<Free<...>>` observes the layer's real (non-)comparability; FD9 item 2 asks to `static_assert(!std::equality_comparable<...>)` on the Free type itself. | `std::equality_comparable<KVFree>` (KVFree = `Free<KVSig::type, int>`, KVSig's layer holding `impure_node`s with `move_only_function` members) evaluates to **true**, not false, on both gcc-16 and clang-23 — confirmed by direct compile (see handoff). The hand-written friend `operator==`'s *declaration* is visible from class-template instantiation independent of whether its *body* would compile, and `std::equality_comparable` only needs the expression `a == b` to resolve (an overload-resolution check, not a body-instantiation check), so it reports true. Actually *calling* `==` on a `KVFree` (a separate, uncommitted scratch probe) does hard-error inside the friend body, exactly as FD3 predicts — but that is a different check than `std::equality_comparable`. Net effect: FD9 item 2's literal `static_assert(!std::equality_comparable<...>)` on the Free type does not hold; the operationally-relevant property ("the TU compiles without ever naming/calling ==") does hold and is what the committed test actually asserts. | `ops/freer/handoffs/01-baseline-gate.handoff.md` |
| DEV-S05-1 | S05 | FD4, FD6 | FD4/FD6 frame the capture-ownership rule as "own captures by move, not reference" and treat `smd::typeclass::mbind`/`Monad::bind` as safe, general-purpose composition for Freer programs (the S04 handoff's ergonomics note explicitly recommends `mbind` for readability, and the S05 dispatch prompt repeats that recommendation for program composition). Neither FD4 nor FD6 records any restriction on what a `bind`-composed continuation may itself capture. | `FreeMonadImpl::bind`'s generic recursive traversal (`free.hpp`, unmodified) re-threads its `Fn` continuation through a **non-`mutable`** inner closure (`[self, fn = std::forward<Fn>(fn)](auto&&child){ return self.bind(child, fn); }`) whenever the right-hand side is impure (a Roll) — so `fn` is accessed as `const Fn&` one level down. Because `.bind` is one generic template body covering both the Pure-leaf and Roll cases for `child`'s fully generic `auto&&` type, the compiler must also instantiate `.bind`'s own impure-branch code at that recursive level, which needs to COPY-construct `Fn` again. A continuation type that owns a move-only `one_shot` (as `discharge`'s re-emitted continuation must, holding the original node's stored `k`) has no copy constructor, so this instantiation is a hard compile error (`use of deleted function one_shot::one_shot(const one_shot&)`), **structurally, regardless of whether that recursive branch is ever taken at runtime**. `mbind` remains fully safe for ordinary user-facing program composition (every continuation in this step's `retry_program()` test, and every prior step's tests, captures only copyable state); the limitation is specific to a continuation that itself embeds a `one_shot`/move-only value, which only infrastructure code (`discharge`, and plausibly S06's pairing) constructs. `discharge`'s re-emit branch works around this by building the re-emitted `impure_node`/`roll_free` directly (mirroring `send`'s own literal aggregate-init construction) instead of routing through `mbind`. | `ops/freer/handoffs/05-rows.handoff.md` |
