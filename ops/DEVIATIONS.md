# Deviation ledger — implementation reality vs. the design

Each row is a place the build taught us something the design didn't
know. The design author reconciles these into
`docs/recursion-schemes-design.md` §3 (decisions log) and the relevant
section. Equivalence-law failures that forced an equation fix (design
§3 D8) belong here too.

| ID | Step | Design section affected | What the design said | What was true | Recommended doc change |
|----|------|------------------------|----------------------|---------------|------------------------|
| DEV-03 | S14 | §7.9 dist_ana, §4 ("distributive laws are... polymorphic function objects... for every X") | `dist_ana`'s wrapping lambda (`dist_laws.hpp`) wrote `smd::typeclass::Identity{x}` and relied on CTAD to deduce the wrapped type, on the assumption this always wraps `x` one level deeper regardless of what `x`'s own type is (as `dist_cata`'s naturality tests, using plain `int`/`char` element types, exercised). | False whenever the distributive law's own element type `A` is itself already an `Identity<T>` — exactly the case S14's `ana_via_gana` needs (`gana<F, Identity<Seed>>(dist_ana, ...)`, generalized.hpp): `Identity{x}` for `x : Identity<T>` invokes CTAD's implicit *copy* deduction candidate ([over.match.class.deduct], the same rule that makes `vector{v}` for `v : vector<int>` copy rather than nest), silently producing `Identity<T>` (a copy of `x`) instead of `Identity<Identity<T>>`. This broke `gana_worker_t`'s type arithmetic (`dist_ana(m)`'s result element type collapsed from the required `Identity<Identity<Seed>>` down to `Identity<Seed>`), caught as a hard `functor_typeclass` instantiation failure (`no type named 'type' in struct std::invoke_result<...>`), not a silent wrong answer. Fixed by naming the wrapped type explicitly (`Identity<std::remove_cvref_t<decltype(x)>>{x}`), sidestepping CTAD entirely; `dist_laws.t.cpp`'s existing tests (plain-element-type only) still pass unchanged. | Note in §7.9/§4 that any natural-transformation/distributive-law body constructing a wrapper type from a generic element via CTAD (`Identity{x}`, and by the same reasoning any other aggregate-wrapper construction from an unconstrained `auto`/template element) must name the wrapped type explicitly rather than relying on CTAD, because CTAD's copy-deduction candidate silently collapses a "wrap one level deeper" intent into "copy" whenever the element happens to already be an instance of the same wrapper template — this is a general C++ hazard, not specific to `dist_ana`, and will recur wherever a generic scheme is instantiated with an already-wrapped element type (as `gana`'s monad-nesting deliberately does). |
| DEV-04 | S14 | §4 / D10 ("all new schemes and supporting types are declared constexpr") | Implied every operation reachable from a scheme body is already `constexpr`-capable where the underlying data allows it — `monad_typeclass`'s `join` (used by `gana`'s worker, generalized.hpp) was assumed to be constexpr like `bind`/`pure` since D10 predates S14 and monad.hpp is S03/S08-vintage. | `Monad<Impl>`'s four CRTP-derived operations (`apply`, `join`, `kleisli`, `bind_with`, `smd/typeclass/monad.hpp`) and the two free functions built on them (`mbind`, `join`) were never marked `constexpr`, even though every `Impl::bind`/`Impl::pure` they forward to (Identity/Free/either/optional) already was — a pre-existing gap that simply had no caller reaching it in a constant expression before S14 (`ana_via_gana_constexpr_smoke`, gana.t.cpp, is the first). Caught as a hard compile error (`call to non-'constexpr' function ... join`), not a silent behavior change. Fixed by adding `constexpr` to all six (purely additive — no signature or behavior change; verified the full 194-test gate stays green). | Note in §4/D10 that typeclass CRTP base classes (Monad, and by the same reasoning Comonad/Applicative if they grow derived operations later) must mark every derived operation `constexpr` at declaration time, not just the `Impl`-provided primitives, even before any scheme actually needs it in a constant expression — the gap is invisible until a later step's `static_assert` first reaches it, exactly as happened here. |
| DEV-01 | S06 | step S06's Pitfalls | "the identity law won't catch a wrong version, but the take-while test will (a wrong version stops too early or too late on `[3,-1,4]`-shaped inputs)" | Empirically false for `take_while_positive`: verified by building both `prepro` and a "shallow" variant (applies the transformation once per node when visited, never cumulatively re-hoisting the whole remaining subtree) side by side — both give `3` on `[3,-1,4]`. The transformation is a monotone single-cut: the decision that collapses a subtree to `Nil` is made the first time any layer of it is inspected, so applying it once per node (in visitation order) is observationally identical to applying it cumulatively for *this* transformation family. A non-idempotent transformation (e.g. `decrement every head by 1`) does discriminate: on `[10,10,10]`, correct cumulative `prepro` gives `27`, the shallow variant gives `28`. | Reword the S06 pitfall (and design §7.4's cumulative-cost note) to require a **non-idempotent** natural transformation for the discriminating test, with `decrement_nat`/`[10,10,10]`-style as the worked example, rather than a monotone cut like take-while. The `[3,-1,4]` take-while test is still worth keeping (it does catch "forgot to hoist at all" — root-only application gives `6` instead of `3`) but should not be relied on as the sole prepro depth-correctness gate. |
| DEV-02 | S12 | §4 ("distributive laws are likewise polymorphic function objects... for every X"), §7.9 | Every distributive law is a single, uniform polymorphic function object, callable with no explicit template arguments at any call site — matching `dist_cata`'s own given code exactly. | Only `dist_cata`, `dist_ana`, and `dist_zygo(helper)` achieve that: their argument type is either a single opaque `Layer`, or wrapped inside a *real* (non-alias) class template (`Identity<Layer>`, `std::pair<B,X>`) that records the needed type directly. `dist_histo`, `dist_futu`, and `dist_para` all have argument types containing a *bare* `F<X>` application; GCC 16 cannot deduce a template-template parameter `F` back out of an already-elaborated alias-template functor family (`NatF`, `IntListF`, ...) — confirmed empirically ("is not derived from const F<...>"). Fix: make each a variable *template* on `F` (`dist_histo<F>`, `dist_futu<F>`, `dist_para<F>`); once `F` is bound, the remaining element type deduces normally. Separately, `dist_apo`/`dist_gapo(coalg)` need an explicit leading `X` (`dist_apo.operator()<X>(e)`) because `make_left`'s result-side type parameter is never deducible from its argument (same as `either.hpp`'s own `make_left`, S03) — the needed `X` never appears in the Left branch's own data. | Note in §4/§7.9 that `dist_histo`/`dist_futu`/`dist_para` are variable templates on `F` (not bare singletons) and that `dist_apo`/`dist_gapo` require an explicit leading element-type argument at their call site. The underlying equations are unchanged; only the call convention differs from what §4's prose implies. |
