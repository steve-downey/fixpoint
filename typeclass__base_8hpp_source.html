11// ===========================================================================
12// The typeclass contract (canonical; the per-concept headers refer here)
13// ===========================================================================
14//
15// A typeclass in this library is a compile-time *dictionary of operations*
16// selected per concrete type -- a shape, not a type. The whole contract that
17// every concept (Functor, Applicative, Monad, Foldable, Traversable, Comonad,
18// ...) and every instance must honor lives here so it is stated exactly once.
19//
20// 1. Shape, not associated type. A typeclass is identified by the set of
21// named operations its dictionary exposes, not by any reified associated
22// type. There is no `Monad::type`; there is only an object that answers
23// `bind`, `pure`, etc. (The only type-level helper is applicative_value_t
24// below, an element-type projection -- not a nominal conformance.)
25//
26// 2. Duck-typed dispatch through a lookup variable. Each concept owns a
27// variable template, e.g. `template<class T> inline constexpr auto
28// functor_typeclass = std::false_type{};`. A concrete type T "has" the
29// concept iff that variable is specialized for T to a dictionary object
30// exposing the required members. The default `std::false_type{}` is the
31// unregistered sentinel; every CRTP base static_asserts against it to give
32// a readable "no *_typeclass<T> specialization found" diagnostic. Generic
33// algorithms call through the looked-up object; membership is structural
34// (the members are present), never nominal.
35//
36// 3. Dictionaries are empty, copyable at zero cost. An instance is an empty,
37// stateless value with static storage: `inline constexpr auto
38// xxx_typeclass<T> = XxxMap<...>{};`. It carries no data members, so it is
39// trivially copyable at no cost -- algorithms may take it by value, by
40// reference, or bind it as a reference NTTP without overhead. Do not give
41// a dictionary state.
42//
43// 4. Names mean the same thing everywhere. An operation name denotes one
44// meaning across every concept that exposes it: `pure` (Applicative,
45// Monad), `apply` (Applicative primitive; Monad-synthesized), `fmap`
46// (Functor; derived on Applicative and Monad) all coincide. This is what
47// lets the concepts share a single object without conflict: a richer
48// concept's dictionary is a *superset* of the weaker ones' surfaces.
49// Never bind a shared name to divergent semantics -- introduce a distinct
50// name or a distinct dictionary/type instead.
51//
52// 5. Object enrichment (the flattened hierarchy). Because names coincide,
53// each concept's object also exposes the surfaces below it, derived once
54// from its primitives: Applicative is-a Functor, Monad is-a Applicative
55// (see the structural chain in apply.hpp / monad.hpp). So a single Monad
56// registration yields a dictionary answering the full Functor +
57// Applicative + Monad surface. Enrichment is at the *object* level only;
58// implicit `*_typeclass<T>` dispatch stays per-concept, so a hand-written
59// per-concept instance remains authoritative for implicit lookup while the
60// monad object always carries the canonical, law-abiding derivations.
61//
62// 6. Lookup is explicit and static; never ADL. Algorithms reach operations by
63// consulting the looked-up dictionary object, not by argument-dependent
64// lookup. Do not add a parallel ADL-only customization path for a concept.
65// Three lookup modes are supported -- implicit lookup, NTTP pinning, and
66// explicit-object -- realized canonically by `layer_fmap` in
67// smd/fixpoint/fmap.hpp; new algorithms should follow that shape.
68//
69// 7. Bases are non-structural; mind deducing-this access. Instances are built
70// as `struct XxxMap : Xxx<XxxImpl<...>> { using XxxImpl::prim; ... };` over
71// a CRTP base `Xxx<Impl> : protected Impl`. The `protected` base makes Map
72// a non-structural type, so NTTP pinning must use a *reference* NTTP
73// (`const auto&`) binding the inline-constexpr variable's static storage
74// (a by-value `auto` NTTP would demand a structural type). A corollary of
75// deducing-this: a `self.member(...)` call is access-checked against
76// `self`'s reified type, so any class-internal helper reached that way must
77// be public (re-exposed via `using` up the chain) or a `detail::` free
78// function -- a private/protected helper becomes inaccessible across a
79// `protected` inheritance link two-plus layers down.
80//
81// Registration recipe: define `XxxImpl` (the primitive operations), define
82// `XxxMap : Xxx<XxxImpl>` re-exposing the primitives via `using`, then
83// `inline constexpr auto xxx_typeclass<ConcreteType> = XxxMap{};`.
84
85template <class T>
86using remove_cvref_t = std::remove_cvref_t<T>;

88/** Trait that extracts the element type from an applicative container.
89 * Primary template uses the nested `value_type` alias when present.
90 */
91template <class T, class = void>
92struct applicative_value;
93
94template <class T>
95struct applicative_value<T,
96 std::void_t<typename remove_cvref_t<T>::value_type>> {
97 using type = typename remove_cvref_t<T>::value_type;
98};
99
100template <class T>
101struct applicative_value<std::optional<T>, void> {
102 using type = T;
103};
104
105/** Convenience alias for `applicative_value<T>::type`. */
106template <class T>
107using applicative_value_t = typename applicative_value<remove_cvref_t<T>>::type;
